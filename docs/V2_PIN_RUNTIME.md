# V2 PIN runtime integration

Migration 005 is ordered after tickets. Migration 013 adds persistent generated Vault PIN storage without changing existing request rows. PIN protection uses AES-256-GCM with a fresh 96-bit IV and authentication tag. `PIN_PROTECTION_KEY` must be a non-example base64 value decoding to exactly 32 bytes when the PIN feature is enabled. Tampered protected values fail authentication. Runtime composition exposes narrow PIN services and the feature manager enforces the player-name dependency.

The Vault panel says "Click below to view or receive your Vault PIN." **Get My Vault PIN** generates a cryptographically random four-digit code once for each guild/user and privately DMs that same code on subsequent retrievals. Common weak sequences are excluded. Users need the configured member role (staff are also eligible) and a verified player name; changing a name requires re-verification before retrieval. When no member role is configured, verified users in the Vault channel can retrieve their own PIN. PINs are private between the player and staff: players receive only their own by DM, while staff can read generated PINs in the configured staff-only directory. No code is returned in ordinary interaction responses, operational activity, process logs, or audit records.

Retrieval is limited to the configured guild/channel and current panel message, with one delivery at a time per user and a 30-second cooldown. Failed DMs preserve the encrypted code for retry; the user is told to allow server-member DMs rather than receiving a public fallback. Durable generated codes are not purged by one-time request retention.

Staff **Generate Missing PINs** is bound to the current PIN dashboard and checks moderation authorization and channel privacy before loading members. It requires the configured member role, Guild Members intent, and Developer Portal Server Members Intent. It skips bots, users with neither the member nor the staff role, unverified names, and existing codes; members holding both roles are counted once. It never sends mass DMs or overwrites a code. One run at a time processes at most 10,000 guild members. A private aggregate result reports generated/existing/skipped/failed counts. Generation and successful player retrieval trigger a directory refresh without posting codes.

With dashboards enabled, `pinsDashboard` is a single directory view of player names and Discord identities, ten per page, with PIN values hidden. There is no PIN Activity tab or historical-custom-PIN disclaimer. **Generate Missing PINs** is its only mutation. Previous / Next appear only for larger directories to preserve bounded SQL queries and Discord message limits; only the selected page is decrypted. Names are escaped and mentions disabled.

**Reveal PINs Privately** is the stream-safe fallback rather than relying on embed spoiler rendering: the standing message never contains a PIN. A fresh, staff-authorized read returns the selected page's codes in an ephemeral response, using normal-message `||spoiler||` formatting. The response is visible only to the requesting moderator; deliberately revealing it while streaming can still disclose a code. Staff reads enforce the configured staff role, guild and PIN dashboard channel at the service boundary, and stale/copied panels cannot reveal codes. Startup uses a separate internal restoration capability, not a caller-supplied authorization bypass. The adapter verifies fresh channel permissions before decryption and again before publication, including non-staff member-specific overwrites. Unreadable records fail the page with a secret-free error rather than showing incorrect codes.

**Custom PIN requests are retired.** The Vault button, modal, submission and staff approve/deliver/cancel runtime handlers are removed. Stale custom buttons or submitted modals return a private retirement notice without reading PIN input or mutating rows. On ready/restart, existing bound, bot-owned custom moderation messages in the configured guild/dashboard are stripped of their controls in batches of 100; missing messages are not recreated. Historical rows and audit events are preserved. Previously pending/approved requests are not claimed as completed or promoted into Vault PINs: existing retention still expires elapsed requests, clears protected material, and later purges eligible terminal records. Delivered/scrubbed/expired custom codes are never reconstructed or displayed. The old domain module remains only for historical compatibility tests, not runtime composition. No slash commands are reintroduced.

The directory is redacted on observed channel/role/member permission changes or verification failures and restored when privacy can be verified again. Discord permission changes and message edits are not atomic: an administrator making the channel public can expose an already-posted message before the bot receives the event, and missing Discord edit permissions can prevent redaction. Restrict permission administration and never make this channel public. Discord administrators and bot integration roles have privileged access; only configured staff-role holders can trigger directory reads. Failed restoration/redaction emits fixed secret-free notices. No live credentials are needed to exercise the regression suite.

Relevant privacy events received while restoration is publishing force a coalesced recheck after that attempt. Listeners are scoped to this guild/channel and audience-relevant role/member changes, including `roleCreate` for new audience-relevant roles and `guildMemberAdd` / `guildMemberAvailable` for overwrite targets; metadata-only and unrelated changes do not reload the directory. Unknown Member (10007) denotes a departed member, not an active viewer; network/permission failures still block publication. Unchanged payloads skip edits. Failed restores retry after 30 seconds and stop retrying at shutdown, so a transient REST failure does not permanently invalidate staff controls. Binding-save failures instead redact the new untracked message and suppress automatic retries to prevent orphan-message loops; repair storage and restart to recover. Paging acknowledges the interaction before privacy checks and returns subsequent errors privately.

If a generated PIN was genuinely delivered but recording its delivery timestamp fails, the service preserves that truthful DM result and emits `pin.vault-delivery-metadata-failed` with a fixed, secret-free reason. Self-service generation, delivery/failure, and aggregate bulk generation are sanitized operational events in the PIN log category; no raw error or credential is stored there.
