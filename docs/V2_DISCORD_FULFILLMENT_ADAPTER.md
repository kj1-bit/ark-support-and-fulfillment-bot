# V2 Discord fulfillment adapter

The Discord boundary converts interactions into validated actor, guild, channel, message, and role context. Fulfillment confirmation details come only from trusted player and catalog services. Confirmation sessions are opaque and server-side. Persisted audit/operational events provide completion logs without raw EOS identifiers, scanning delays are displayed, and public errors do not reveal internal database or transport details.

The standing **Dino Fulfillment** panel provides **Browse Dino Catalog** and **Search Dino**. An authorized private wizard pages through catalog results and trusted online players across maps, then shows **Review Dino Fulfillment** with **Confirm Spawn** (danger) / Cancel. There is no fulfillment map-selection step. Scans include only enabled servers allowlisted for both player listing and fulfillment. Catalog pages contain 10 creatures; player menus contain up to 25 entries with Previous/Next. Each player page rescans live state. Servers are scanned sequentially to bound RCON load; an unavailable map fails the scan visibly instead of silently omitting players. Selection lifetimes start after scanning completes. Each opaque player reference retains its observed server, displayed beside the player name, and confirmation revalidates that exact identity on that server. Linking does not bypass any fulfillment checks.

Wizard steps are actor/guild/channel/message-bound and expire after two minutes; abandoned pre-review selection does not create a fulfillment request. The review issues the existing single-use confirmation token against that exact private message, retaining catalog-version checks and allowlisted execution. Cancellation after review uses the same existing token-bound service. The retired `/dino-fulfillment` and `/player-link` slash commands are no longer handled.

## Staff identity management

The public panel offers only **Set My In-Game Name**. Staff use the separate private request panel in `pinsDashboard`: **Link Player** selects an unlinked request, then shows exact and close remembered-name matches, with **Refresh** and **Browse All Remembered Players** fallbacks. At most 25 matches are shown; already-owned identities show **Already linked** without exposing their owner. Every link requires **Confirm Link**. Observations from enabled, listing-allowlisted maps persist by EOS ID in SQLite, survive restarts, and refresh after startup and every three minutes while `playerNames` is enabled. Live fulfillment scans also remember observations on a best-effort basis: failed writes emit one sanitized `player-observation.persistence-failed` event per map scan, with no EOS ID, player name or error details, and never prevent online selection or revalidation. Background checks are sequential and non-overlapping; map failures log `player-observation.failed` without transport details, preserve remembered entries, and do not prevent checks of later maps. Shutdown clears the timer and drains the current check before closing SQLite. There is no observation-expiry policy or extra configuration; see [retention exclusions](V2_RETENTION.md#not-purged-automatically).

**Enter EOS Manually** opens **Link Player Manually**, with the submitted name prefilled and an **EOS ID (32 hexadecimal characters)** field. This allows linking a never-observed player. EOS input is strictly validated and stored lowercase; raw IDs are never echoed in responses. Mock mode's simulated online player is **Mock Test Player**.

Linking approves the submitted name in the same transaction as the trusted EOS association. An already-linked Discord member or identity is blocked until staff unlink it. Link/unlink mutations are serialized; the in-memory registry changes only after successful persistence. **Unlink Player** requires confirmation and returns an existing submitted name to pending without deleting PINs, tickets, observations or history. Old online selections no longer authorize fulfillment after unlinking.

Every link, manual modal submission and unlink step requires `player-names.verify` and the same actor/guild/channel/private-message/expiry binding. Controls are single-use; changed links invalidate old unlink reviews. Restart discards wizards but not remembered identities or trusted links. Audit events record `player-link.created` / `player-link.removed` without raw EOS IDs.

The SQLite session adapter exposes the domain `requestId` from persisted `request_id`, retaining the legacy field for existing ticket consumers. Previously confirmation/cancellation read only `requestId` while SQLite returned only `request_id`: review succeeded but completion failed before execution and before a completion event. The router also swallowed that failure without logging it. Confirmation and cancellation now resolve the persisted binding; router exceptions emit secret-free `discord.interaction.failed` diagnostics. Completion, failed execution, uncertain execution, offline targets, revalidation errors, catalog expiry and cancellation remain auditable. A failed pre-execution revalidation becomes FAILED, never a stuck CLAIMED request; possible execution remains UNCERTAIN and must not be blindly retried.

Regression coverage uses real disposable SQLite composition and simulated Discord/RCON: success, cancellation, failure, uncertainty, offline/revalidation errors, replay and context/role mismatches. It does not log into Discord or contact an ARK server.
