# V2 PIN runtime integration

Migration 005 is ordered after tickets. Migration 013 adds persistent generated Vault PIN storage without changing existing request rows. PIN protection uses AES-256-GCM with a fresh 96-bit IV and authentication tag. `PIN_PROTECTION_KEY` must be a non-example base64 value decoding to exactly 32 bytes when the PIN feature is enabled. Tampered protected values fail authentication. Runtime composition exposes narrow PIN services and the feature manager enforces the player-name dependency.

The Vault panel says "Click below to view or receive your Vault PIN." **Get My Vault PIN** generates a cryptographically random four-digit code once for each guild/user and privately DMs that same code on subsequent retrievals. Common weak sequences are excluded. Users need the configured member role (staff are also eligible) and a verified player name; changing a name requires re-verification before retrieval. When no member role is configured, verified users in the Vault channel can retrieve their own PIN. No code is returned in interaction responses, log panels, or audit records.

Retrieval is limited to the configured guild/channel and current panel message, with one delivery at a time per user and a 30-second cooldown. Failed DMs preserve the encrypted code for retry; the user is told to allow server-member DMs rather than receiving a public fallback. Durable generated codes are not purged by one-time request retention.

Staff **Generate Missing PINs** is bound to the current PIN dashboard and checks moderation authorization before loading members. It requires the configured member role, Guild Members intent, and Developer Portal Server Members Intent. It skips bots, users with neither the member nor the staff role, unverified names, and existing codes; members holding both roles are counted once. it never sends mass DMs or overwrites a code. One run at a time processes at most 10,000 guild members. A private aggregate result reports generated/existing/skipped/failed counts, allowing a retry after partial failures without revealing credential material.

**Request a Custom PIN** retains the existing chosen-code request modal and staff approval/private-delivery/cancellation service. Pending requests expose staff-only Approve / Deliver by DM / Cancel controls in `pinsDashboard`; delivery is authorized in the Vault or PIN dashboard channels. Control-message guild/channel/message bindings persist in `pin_request_messages`, with restart recovery in batches of 100 and live recreation of deleted controls. Stale controls cannot act on a relinked, closed, or expired request. Unlike generated codes, these one-time request codes are cleared after delivery/cancellation/expiration. All PIN values stay private throughout both workflows. The retired `/pin` slash command is no longer handled; the Vault panel and these bound staff buttons are the only PIN paths.

If a generated PIN was genuinely delivered but recording its delivery timestamp fails, the service preserves that truthful DM result and emits `pin.vault-delivery-metadata-failed` with a fixed, secret-free reason. Self-service generation, delivery/failure, and aggregate bulk generation are sanitized operational events in the PIN log category; no raw error or credential is stored there.
