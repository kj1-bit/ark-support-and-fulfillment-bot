# V2 ticket runtime integration

Migration 004 is ordered after player names. Runtime composition constructs the SQLite ticket repository and narrow ticket service, adds centralized ticket-moderation authorization, and exposes tickets without exposing the database. The Discord feature manager registers tickets only when both tickets and the required player-name feature are enabled.

Migration 012 adds channel provisioning/status, source channel, control-message ID, completion timestamp, and a durable number counter. Existing record-only V2 tickets are preserved without retroactively creating channels; they no longer block a new private request, and migration 012 replaces the old per-type open-ticket index with the per-requester private-request index. The standing **Open Request** button reserves a single active private request per guild/user before creating a private channel under `discord.channels.ticketCategory`. The retired `/ticket` slash command is no longer handled; see [command retirement](V2_GUIDE.md#retiring-the-old-slash-commands).

With tickets enabled, a separate **Legacy ticket management** panel is restored in `ticketLogs`, even if dashboards are disabled. Staff press **Manage Legacy Ticket** and enter a preserved ticket ID from staff audit records (the simplified Discord ticket log no longer displays IDs). A private view shows its original details and the actions available for its current state: Claim / Ticket Completed / Close while open, completion/closure after claiming, closure after completion, and Reopen after closure. Viewing or upgrading never changes a legacy record's status or creates a channel. Closing records its timestamp and makes it eligible for `retention.closedTicketDays`; reopening clears completion and makes it active again without creating a channel.

Legacy lookup modals are bound to the initiating staff member, guild, channel, and current standing panel, expire after two minutes, and must be restarted after a process restart. Action tokens use the existing persisted, single-use session store, are bound to the staff member/guild/log-channel/private-message/action/ticket, and expire after two minutes. Every lookup and action checks the centralized `tickets.moderate` capability and configured guild/log channel at the service boundary; requester ownership does not bypass staff authorization. A legacy control cannot operate on a private-channel ticket. The standing panel and each interaction also require verified staff-only channel permissions.

The Discord gateway explicitly denies `@everyone`, grants requester/staff/bot access, posts the opening/DLC notice, and persists the control-message binding. Requester-visible messages contain no ticket reference or claiming moderator; action acknowledgments are private and contain no record dump. Existing opening messages are rewritten on sync/recovery to remove old reference text. The internal channel topic, durable number and control IDs remain for ownership/recovery. While a ticket is unassigned, staff can press **Claim Ticket**; claiming is staff-only and the button disappears once claimed. Assignment identity appears only on staff-only surfaces: Ticket logs (Refresh Logs) and Open Tickets. Logs show opening, claim/release and closure identities without record dumps. Full audit events remain intact, with an explicit acting user for new transitions. **Ticket Completed** is staff-only and leaves the channel active. **Close Ticket** accepts the requester or staff, denies requester access, renames the archived channel, and retains staff access. Staff reopening restores requester access only if there is no newer active request.

## Open Tickets and unclaim

The tickets feature owns a separate persistent **Open Tickets** embed in the existing `ticketLogs` channel, beside Ticket logs (when dashboards are enabled) and Manage Legacy Ticket. It works with dashboards disabled and needs no new configuration or migration: the SQLite schema remains 13. Startup, message deletion and restart restore its persisted `open-tickets` binding.

The panel lists every ticket in this guild whose stored state is not CLOSED, including completed-but-not-closed and channel-less legacy tickets. Bounded SQL pages contain five entries ordered by creation time and ID. Numbered entries show only requester mention, escaped player name, assignment and channel link. A completed entry prefixes its assignment with `Completed - `; a legacy entry says `Legacy ticket - no channel` instead of linking to the old request channel. A provisioning entry says `Channel pending`. Empty panels say `No open tickets.` Previous / Next appear only for multiple pages. Matching numbered **Unclaim 1**, **Unclaim 2**, etc. buttons appear for every entry; already-unclaimed entries have disabled buttons. Mentions never ping. No descriptions, record IDs, timestamps or ages are displayed.

Only staff may read/page or unclaim. Fresh role permissions and member-specific overwrites are verified using the shared private-staff-channel validator before publication and actions. Unknown permissions or non-staff visibility fail closed, redact the bound panel and invalidate its controls; observed permission changes trigger a recheck. Staff-only restoration also verifies bot ownership of the saved message. As with the PIN panel, Discord permission changes and redaction are not atomic; keep permission administration restricted. Discord administrators and bot integration roles retain their privileged access.

Unclaim checks the configured guild/log channel, staff capability and current persisted panel message at the service boundary. The adapter additionally binds an opaque entry token to the ticket on the displayed page. Buttons from old pages, deleted/replaced panels or earlier processes cannot operate on another numbered entry. Stored state, never the displayed assignment, decides the action. Any authorized staff member may unclaim; it is not restricted to the claimant. An atomic, state-and-previous-claimant-guarded SQL update clears the assignment and restores OPEN. In-process per-ticket locks serialize claim/unclaim with completion and closure, while the SQL guard prevents clearing a concurrently replaced claimant or a closed ticket.

The acting moderator receives the ephemeral reply `Ticket unclaimed.` Already-unclaimed and closed tickets are private no-ops (`This ticket is already unclaimed.` / `This ticket is already closed.`); an entry removed from the current page returns `This Open Tickets entry is no longer available.` No requester-visible message identifies the claimant or the releasing moderator. State-driven channel synchronization restores **Claim Ticket**, retaining the existing permission and rename behavior. A sync failure is audited and retryable without a second unclaim event; startup channel recovery also repairs controls.

Completion and assignment are independent: unclaiming a completed ticket keeps its completion timestamp and `Completed` label. **Claim Ticket** returns, but **Ticket Completed** stays disabled. Staff may claim that completed-but-open ticket without completing it again. New completion/closure actions preserve the existing claimant rather than replacing it with the acting moderator; reopening clears the old claimant and completion. Existing historical moderator values are not rewritten; older versions may have overwritten them during completion.

Create, claim, unclaim, complete, close, reopen and channel recovery/deletion notify the panel through the ticket service. A 150 ms debounce coalesces bursts, and unchanged payloads skip edits. Shutdown cancels pending refresh timers and removes subscriptions/listeners. No deployment or Discord connection is needed for the real-SQLite and simulated-Discord regression tests.

Every successful release records `ticket.unclaimed` with the acting staff member and previous claimant. The simplified Ticket logs panel additionally displays one line such as `@Moderator unclaimed @Mud's (Mud) ticket.` This release line is a deliberate addition to the earlier opener/claimant/closer-only log design so a claim is not left looking active after release; other internal events remain hidden and full audit history stays intact.

The bot needs View Channel, Send Messages, Read Message History, Manage Channels, and Manage Roles (shown as Manage Permissions on channels) in the ticket category. The bot's own channel overwrite grants only View Channel, Send Messages, Read Message History, and Manage Channels; it never grants Manage Messages or Manage Roles, which Discord would refuse unless the bot already held them. Ticket creation checks these permissions in the category first and fails with a clear private message, without creating a channel. Close and reopen check them in the ticket channel before changing the ticket. Startup recovery audits any missing permissions as `ticket.channel_failed` with phase `permissions` and logs `discord.ticket.restore_failed` with the missing permission names. If a close or reopen is saved but its Discord sync later fails (phase `archive` or `reopen`), the channel status stays behind the ticket state. Pressing the same button again re-applies the sync without a second transition, and startup recovery retries it too. A failed close therefore never silently leaves requester access in place.

Access and control updates happen before the channel rename. Renames run in the background and never hold the per-ticket lock, because Discord allows only about two renames per channel every ten minutes. Rapid close/reopen changes collapse into the latest desired name (`closed-<number>-<name>` while closed, the original name when open). A failed rename is logged as `discord.ticket.rename_failed` and is re-applied by the next sync or startup recovery.

Moderation inside dynamic ticket channels first checks the stored guild/channel/message and then the centralized staff capability; it does not trust a custom ID or category membership alone. Startup reconciles interrupted provisioning and missing controls. Deletion events recreate bound controls or mark a manually deleted channel closed/deleted. Retention deletes an expired archived channel before purging its row; a Discord failure leaves the row available for retry. See [V2 retention](V2_RETENTION.md).
