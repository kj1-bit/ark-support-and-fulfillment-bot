# V2 operational dashboard runtime integration

Migration 006 creates the operational-event store; migration 009 stores the IDs of persistent Discord log-panel messages. Runtime composition constructs the event repository, event service, narrow dashboard service, and panel-message repository. Supported audit events are sanitized before persistence, and persistence failures emit only a generic external audit notice.

Set `features.dashboards` to `true` to enable the panels. The feature requires the staff role and all three log channels: `ticketLogs`, `pinsDashboard`, and `fulfillmentLogs`. After Discord becomes ready, it edits each saved panel or creates and persists a replacement. A deletion event for an active panel triggers immediate recreation. Restarting the process restores the same saved messages where they still exist.

Ticket logs show who opened (requester and player name), claimed, unclaimed and closed a ticket, without raw JSON, descriptions, references or completion/internal events. Assignment identity appears only on staff-only surfaces, not in the requester's channel. The deliberate extra release line says `@Moderator unclaimed @Mud's (Mud) ticket.` so an earlier claim does not look active after release. Filtering happens before SQL pagination/counting; the full audit history is retained. Historical records accept both SQLite and domain identity fields, and new actions explicitly record the acting user, including requester closure.

The tickets feature, not dashboards, owns the separate **Open Tickets** panel alongside these logs and Manage Legacy Ticket. It lists all nonclosed tickets in this guild, including completed and legacy entries, in pages of five with numbered Unclaim buttons and channel links. Assignment changes are service-authorized and audited; unsafe channel permissions redact its contents. It refreshes automatically after ticket changes, survives restart/message deletion, and works even with dashboards disabled. See [ticket runtime](V2_TICKET_RUNTIME.md#open-tickets-and-unclaim).

Fulfillment panels show sanitized paged activity **inline**. When PINs are enabled, the PIN panel is a single ten-row **Vault PIN directory** with escaped player names, Discord identities and hidden codes. There is no PIN Activity tab. **Generate Missing PINs** remains available with separate staff authorization and current-panel binding. **Reveal PINs Privately** returns a fresh selected page only in an authorized ephemeral response, with normal-message spoilers; PINs are never embedded in the standing directory. Previous / Next appear only for directories exceeding one page, preserving bounded SQL paging and Discord limits. Generation and player retrieval refresh the directory. Custom requests are never promoted to Vault PINs; historical events remain stored but are not a directory UI. Deleting or recreating panels does not modify PINs or event history. With PINs disabled, the panel only states that Vault PINs are disabled. Disabled dashboards register no listeners and perform no Discord network activity.

Because standing logs are not ephemeral, channels must be staff-only. The adapter verifies effective role visibility on restoration and interaction, excluding Discord administrators' inherent access and bot integration roles (managed roles tagged with a bot ID). Booster and other non-staff roles still block rendering. If privacy cannot be verified, it logs restoration failure rather than publishing sensitive events. Previous, Refresh, and Next use distinct custom IDs (`v2:dashboard:<key>:prev|refresh|next:<page>`) because Discord rejects messages with duplicate custom IDs, even on disabled buttons. Each paging button must belong to the currently tracked panel message in its configured guild/channel, and `dashboards.view` is checked before the message is updated. Interaction errors are private and never replace the public log panel with an error or a success-shaped fallback.

The shared persistent-panel lifecycle also restores the user-facing request, Vault, IGN, and fulfillment panels under distinct repository keys. Panel deletion/recreation changes only the stored message reference, not tickets, PINs, trusted associations, or fulfillment history.

PIN directory reads additionally enforce staff role + configured guild + `pinsDashboard` in the service. A distinct internal capability is used for startup restoration only after destination verification. Fresh channel/role permissions and member-specific overwrites are checked before decryption and again before publishing; unverifiable permissions fail closed. Bound PIN panels must belong to this bot, are redacted on observed permission changes/failed restoration, and are recreated only in verified destinations. Deferred-update errors use private follow-ups, never error edits to the standing panel. Channel privacy cannot be changed atomically with Discord message redaction; protect channel administration and review `discord.panel.redaction_failed` notices. See [PIN runtime](V2_PIN_RUNTIME.md) for limitations and historical-request retirement.

Privacy listeners ignore foreign guilds, unrelated channels and metadata-only updates. Audience-relevant role changes/creation, channel overwrite changes and relevant member-role/rejoin/availability events trigger verification, including `roleCreate` and `guildMemberAvailable` for previously uncached members with overwrites. Events received during a pending restore coalesce into a follow-up restore rather than being dropped during publication. Unchanged payloads do not issue another message edit. Failed sensitive restores redact the panel and retry automatically after 30 seconds, without requiring an unrelated event; shutdown cancels retries. A binding-save failure is an exception: its new untracked message is redacted and automatic retries are suppressed to avoid repeatedly creating orphan panels. After fixing panel storage, restart the bot to restore the panel. A departed overwrite target is ignored only when Discord returns Unknown Member (10007), and rejoining that member triggers verification again. Other member lookup failures remain fail-closed. PIN paging defers the update before any privacy REST calls, and all later failures are private follow-ups.
