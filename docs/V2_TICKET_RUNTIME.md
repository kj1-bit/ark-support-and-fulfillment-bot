# V2 ticket runtime integration

Migration 004 is ordered after player names. Runtime composition constructs the SQLite ticket repository and narrow ticket service, adds centralized ticket-moderation authorization, and exposes tickets without exposing the database. The Discord feature manager registers tickets only when both tickets and the required player-name feature are enabled.

Migration 012 adds channel provisioning/status, source channel, control-message ID, completion timestamp, and a durable number counter. Existing record-only V2 tickets are preserved without retroactively creating channels; they no longer block a new private request, and migration 012 replaces the old per-type open-ticket index with the per-requester private-request index. Outside mock mode, the standing **Open Request** button reserves a single active private request per guild/user before creating a private channel under `discord.channels.ticketCategory`. The retired `/ticket` slash command is no longer handled; see [command retirement](V2_GUIDE.md#retiring-the-old-slash-commands).

## Mock-only multiple requests

Only strict `runtime.mode === 'mock'` allows a requester to open multiple active private tickets, including concurrent opens and reopening while another ticket is active. Every other mode (including missing/unrecognized modes in internal composition) preserves the one-active-request rule, counting provisioning, claimed and completed-but-not-closed private requests across all ticket types. Production configuration validation still rejects missing/invalid modes. Verification, guild/channel authorization, private permissions, audit behavior, unique channel bindings and durable ticket numbering are unchanged. This exception does not change RCON transport/mode, allowlists or live configuration.

Forward migration **014, mock-ticket-multiplicity**, raises SQLite to **14**; released migrations 001-013 are unchanged. It adds `mock_multiple` with a checked default of 0, preserving existing rows, channels, panel bindings and the counter. Only mock-mode private reservations/reopens set it to 1. The unique active-request index remains installed for ordinary rows in every runtime mode; it is not globally toggled on startup. Non-mock INSERT/reservation and reopen use single-statement guards against *all* other active private rows, including mock-created ones. SQLite serializes these writes across service instances/connections, not merely in-process locks. A normal-mode reopen resets the marker to 0; claiming, completion and unclaim preserve the existing marker.

Switching a database from mock to test/production never auto-closes/deletes duplicate historical mock requests or their channels. Existing tickets remain readable/moderatable and listed in Open Tickets. A new create or closed-ticket reopen is blocked whenever that requester already has an active private ticket; after all their active tickets close, one new create/reopen may succeed. An already-applied reopen whose Discord sync failed retries synchronization rather than adding a ticket. In mock, another Open Request click deliberately creates another request, not a duplicate-retry alias. Interrupted provisioning/control recovery remains bound to its original record. Failed reservations consume their durable number; retries allocate a new number, and reopening preserves the old number. Back up before schema 14; older schema-13 binaries cannot safely run against the upgraded database, so rollback requires the pre-upgrade backup.

The separate Legacy Ticket Management panel and its lookup modal/action runtime have been removed. No historical ticket rows, migration tables or audit records are deleted or rewritten by this removal. Nonclosed record-only tickets still appear in **Open Tickets** as `Legacy ticket - no channel` and retain its existing staff-only Unclaim behavior. They no longer have Discord claim/complete/close/reopen controls. Consequently, historical rows that were not already closed remain open and are not eligible for closed-ticket retention; no automatic closure or data migration is performed. Already-closed rows retain their normal cutoff-based retention behavior.

On ready/startup with tickets enabled, the bot removes only the message bound as `legacy-tickets`, after verifying its saved channel matches configured `ticketLogs`, the fetched channel belongs to the configured guild, and the message ID/channel/guild and author match the binding and current bot. It never searches for similarly named messages or deletes foreign/unowned messages. An already-missing message clears only that exact persisted binding. Binding removal is guarded against concurrent replacement. Fetch, identity, deletion or persistence failures emit sanitized `discord.ticket.legacy_panel_cleanup_failed` with the failing phase and keep the binding for a later ready/restart retry; missing/unverifiable channels are not assumed safe. The removed panel is never recreated. Old buttons and submitted modals receive only the ephemeral notice `Legacy ticket management has been removed. Use Open Tickets for current assignments.` They cannot read records, consume old action sessions or mutate tickets. Existing sessions expire through normal session retention.

The Discord gateway explicitly denies `@everyone`, grants requester/staff/bot access, posts the opening/DLC notice, and persists the control-message binding. Requester-visible messages contain no ticket reference or claiming moderator; action acknowledgments are private and contain no record dump. Existing opening messages are rewritten on sync/recovery to remove old reference text. The internal channel topic, durable number and control IDs remain for ownership/recovery. While a ticket is unassigned, staff can press **Claim Ticket**; claiming is staff-only and the button disappears once claimed. Assignment identity appears only on staff-only surfaces: Ticket logs (Refresh Logs) and Open Tickets. Logs keep opening and lifecycle actors on one comma-separated line per ticket without record dumps. Full audit events remain intact, with an explicit acting user for new transitions. **Ticket Completed** is staff-only and leaves the channel active. **Close Ticket** accepts the requester or staff, denies requester access, renames the archived channel, and retains staff access. Staff reopening restores requester access; outside mock mode, another active private request blocks the transition.

## Open Tickets and unclaim

The tickets feature owns a separate persistent **Open Tickets** embed in the existing `ticketLogs` channel, beside Ticket logs (when dashboards are enabled). It works with dashboards disabled and needs no new channel or setting. The panel/removal UI itself needs no migration; the mock-only multiplicity change uses schema 14 above. Startup, message deletion and restart restore its persisted `open-tickets` binding.

The panel lists every ticket in this guild whose stored state is not CLOSED, including completed-but-not-closed and channel-less legacy tickets. Bounded SQL pages contain five entries ordered by creation time and ID. Numbered entries show only requester mention, escaped player name, assignment and channel link. A completed entry prefixes its assignment with `Completed - `; a legacy entry says `Legacy ticket - no channel` instead of linking to the old request channel. A provisioning entry says `Channel pending`. Empty panels say `No open tickets.` Previous / Next appear only for multiple pages. Matching numbered **Unclaim 1**, **Unclaim 2**, etc. buttons appear for every entry; already-unclaimed entries have disabled buttons. Mentions never ping. No descriptions, record IDs, timestamps or ages are displayed.

Only staff may read/page or unclaim. Fresh role permissions and member-specific overwrites are verified using the shared private-staff-channel validator before publication and actions. Unknown permissions or non-staff visibility fail closed, redact the bound panel and invalidate its controls; observed permission changes trigger a recheck. Staff-only restoration also verifies bot ownership of the saved message. As with the PIN panel, Discord permission changes and redaction are not atomic; keep permission administration restricted. Discord administrators and bot integration roles retain their privileged access.

Unclaim checks the configured guild/log channel, staff capability and current persisted panel message at the service boundary. The adapter additionally binds an opaque entry token to the ticket on the displayed page. Buttons from old pages, deleted/replaced panels or earlier processes cannot operate on another numbered entry. Stored state, never the displayed assignment, decides the action. Any authorized staff member may unclaim; it is not restricted to the claimant. An atomic, state-and-previous-claimant-guarded SQL update clears the assignment and restores OPEN. In-process per-ticket locks serialize claim/unclaim with completion and closure, while the SQL guard prevents clearing a concurrently replaced claimant or a closed ticket.

The acting moderator receives the ephemeral reply `Ticket unclaimed.` Already-unclaimed and closed tickets are private no-ops (`This ticket is already unclaimed.` / `This ticket is already closed.`); an entry removed from the current page returns `This Open Tickets entry is no longer available.` No requester-visible message identifies the claimant or the releasing moderator. State-driven channel synchronization restores **Claim Ticket**, retaining the existing permission and rename behavior. A sync failure is audited and retryable without a second unclaim event; startup channel recovery also repairs controls.

Completion and assignment are independent: unclaiming a completed ticket keeps its completion timestamp and `Completed` label. **Claim Ticket** returns, but **Ticket Completed** stays disabled. Staff may claim that completed-but-open ticket without completing it again. New completion/closure actions preserve the existing claimant rather than replacing it with the acting moderator; reopening clears the old claimant and completion. Existing historical moderator values are not rewritten; older versions may have overwritten them during completion.

Create, claim, unclaim, complete, close, reopen and channel recovery/deletion notify the panel through the ticket service. A 150 ms debounce coalesces bursts, and unchanged payloads skip edits. Shutdown cancels pending refresh timers and removes subscriptions/listeners. No deployment or Discord connection is needed for the real-SQLite and simulated-Discord regression tests.

Every successful release records `ticket.unclaimed` with the acting staff member and previous claimant. Ticket logs now displays one line per ticket, not a separate line per action: `@Mud (Mud) opened a ticket, @Moderator unclaimed the ticket.` Only the latest assignment action appears; reclaim replaces unclaim and repeated releases retain only the last actor. Completed and closed phrases append to that same line in action order. Reopening clears the earlier assignment/completed/closed phrases and appends who reopened. SQLite pages by ticket, newest-opened first, and successful persisted lifecycle events trigger a debounced refresh. Full audits and retention remain intact; see [dashboard runtime](V2_DASHBOARD_RUNTIME.md) for old/partially expired history handling.

The bot needs View Channel, Send Messages, Read Message History, Manage Channels, and Manage Roles (shown as Manage Permissions on channels) in the ticket category. The bot's own channel overwrite grants only View Channel, Send Messages, Read Message History, and Manage Channels; it never grants Manage Messages or Manage Roles, which Discord would refuse unless the bot already held them. Ticket creation checks these permissions in the category first and fails with a clear private message, without creating a channel. Close and reopen check them in the ticket channel before changing the ticket. Startup recovery audits any missing permissions as `ticket.channel_failed` with phase `permissions` and logs `discord.ticket.restore_failed` with the missing permission names. If a close or reopen is saved but its Discord sync later fails (phase `archive` or `reopen`), the channel status stays behind the ticket state. Pressing the same button again re-applies the sync without a second transition, and startup recovery retries it too. A failed close therefore never silently leaves requester access in place.

Access and control updates happen before the channel rename. Renames run in the background and never hold the per-ticket lock, because Discord allows only about two renames per channel every ten minutes. Rapid close/reopen changes collapse into the latest desired name (`closed-<number>-<name>` while closed, the original name when open). A failed rename is logged as `discord.ticket.rename_failed` and is re-applied by the next sync or startup recovery.

Moderation inside dynamic ticket channels first checks the stored guild/channel/message and then the centralized staff capability; it does not trust a custom ID or category membership alone. Startup reconciles interrupted provisioning and missing controls. Deletion events recreate bound controls or mark a manually deleted channel closed/deleted. Retention deletes an expired archived channel before purging its row; a Discord failure leaves the row available for retry. See [V2 retention](V2_RETENTION.md).
